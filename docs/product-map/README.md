# Карта продукта: начальная проекция

Это начальный инструмент для работы над #688, а не завершённая карта.
Источники истины и разделение доказательств описаны в [ADR-032](../adr/ADR-032-product-map-authority.md).
Он читает `tools/qa/local_features/features.json`, проверяет существующие
правила parity и выводит текущие сценарии без копии реестра:

```sh
python -m tools.product_map validate-parity
python -m tools.product_map matrix
python -m tools.product_map compare --platform web --platform windows --scope voice
python -m tools.product_map generate
python -m tools.product_map generate --check
python -m tools.product_map impact --base <точный-SHA-базового-коммита>
python -m tools.product_map check-transition --base <точный-SHA-базового-коммита>
python -m tools.product_map.ownership.run --base <точный-SHA-базового-коммита>
python -m tools.product_map.ownership.report
```

`impact` показывает компоненты и функции, связанные с изменёнными файлами,
и зависимые функции; при переименовании учитываются оба пути. Исходные пути
без сопоставления перечисляются отдельно. Отчёт диагностический: полный
ownership-каталог ещё не готов, поэтому `coverage` всегда `INCOMPLETE`,
отсутствие функции в отчёте не доказывает отсутствие влияния. В PR CI
печатает отчёт, но пока не блокирует неразмеченные пути.

Отдельная проверка `ownership.run` отклоняет новые runtime-файлы в выбранных
деревьях сервера, Web, Flutter, платформенных адаптеров, контрактов и
инфраструктуры, если ни один связанный с функцией компонент их не содержит.
При переименовании новый путь также проверяется. Базовые существующие файлы
пока не считаются классифицированными: это начальный gate, а не полный аудит
покрытия и не проверка изменений в уже существующих неразмеченных файлах.
`ownership.report` считает отслеживаемые Git пути внутри этих деревьев за
исключением файлов с распознанными суффиксами тестов,
сколько из них связано с функциями, и показывает примеры оставшихся путей по
областям. В деревья входят конфигурация и ресурсы, поэтому это не оценка числа
исполняемых файлов. Отчёт привязан к SHA и требует чистых каталога и parity.
Для вручную проверенных возможностей каталог может указывать узкое дерево
`owned_roots` с конкретным компонентом. Проверка отвергает агрегатные,
пересекающиеся и внешние пути; impact и отчёт учитывают эти связи.

`check-transition` читает каталог непосредственно из Git на указанном SHA и
отклоняет исчезновение существующих ID, снижение ревизии или переписывание
её истории. Если в базовом коммите каталога ещё нет, проверка начинает с
пустой базы. В CI она блокирует нарушения для PR и merge queue; это не заменяет
пока отсутствующий полный контроль покрытия путей и манифеста изменений.

В release workflow Windows, macOS и Android после действующей проверки
настоящих native-артефактов команда `release-snapshot` готовит отдельный
`feature-snapshot.json` в `.out/native-release/<platform>/`. Он содержит
SHA исходников, SHA проверенного manifest и независимые состояния функций;
существующий подписанный пакет и перечень его файлов не изменяются. Sidecar
сохраняется среди workflow evidence. Публикация и runtime в нём остаются
UNKNOWN/NOT_VERIFIED: наличие snapshot само по себе не подтверждает выпуск.
Пути для Web и iOS, приёмка на реальных артефактах и чтение release/deploy
receipts картой пока не реализованы.

Взаимную согласованность трёх локальных записей проверяет команда:

```sh
python -m tools.product_map match-publication --snapshot SNAPSHOT --contract CONTRACT --receipt RECEIPT
```

Она сопоставляет исходный SHA, платформу, хеш manifest, релизную идентичность
и попытку workflow. Даже при совпадении ответ остаётся `MATCHED_UNVERIFIED`,
а выпуск — `UNKNOWN`: происхождение локальных файлов ещё не подтверждено
проверенной GitHub API и проверкой целостности artifact.

Метаданные конкретного native workflow и candidate artifact можно прочитать
непосредственно из GitHub API (при необходимости используется `GITHUB_TOKEN`
из окружения, без вывода токена):

```sh
python -m tools.product_map native-release-candidate --platform windows --run-id RUN_ID --tag windows-v1.0.52
```

Проверяются репозиторий, SHA, попытка и digest. Флаг `--inspect-archive`
дополнительно скачивает и проверяет ограниченный ZIP в памяти; токен на
адрес хранилища не передаётся. Для скачивания может потребоваться токен с
правом чтения Actions. Флаг `--verify-release` после `--inspect-archive`
сопоставляет GitHub Release, все файлы и разрешённый до коммита тег с архивом.
Результат остаётся `LIVE_RELEASE_MATCHED_UNVERIFIED`: проверка на настоящем
новом артефакте и полное подтверждение происхождения ещё не выполнены.

Команда `generate` создаёт автономный предварительный просмотрщик
`docs/product-map/generated/index.html`. Его можно открыть в браузере без
сервера; поиск и ссылки вида `#feature/voice.long_recovery` работают локально.
Для GitHub и чтения без JavaScript также генерируются [матрица и карточки](generated/index.md).
В карточке показаны зарегистрированные компоненты и направленные связи
`зависит от`; отсутствие связи означает недостаток данных, а не её отсутствие
в приложении. Это пока не полная архитектурная схема.
Системная схема берёт вручную проверяемые узлы и связи из
`product-map/architecture/system.json`: существование путей и структура
проверяются при генерации. Четыре native-адаптера связаны с одним общим
Flutter-компонентом. Ссылки ведут на текущую ветку master без привязки к SHA;
наличие тестового файла не подтверждает прохождение теста или работу в среде.
Отсутствующие компоненты и связи остаются неинвентаризированными.
В матрице можно выбрать платформу, область и состояние, а также независимо
показывать исходники, релиз и runtime. Фильтр расхождений относится к исходникам;
UNKNOWN не превращается в доказанное отставание.
Проверка `--check` обнаруживает устаревший файл и запускается в CI. Она
проверяет только эту проекцию, а не полноту карты или достоверность релизов.

В выводе отдельно представлены состояние исходного кода, релиз и runtime.
`UNKNOWN` означает отсутствие подтверждённой информации, а не отсутствие
функции. Объявленный в старом реестре runtime `PASS` показывается отдельно и
не считается подтверждённым новой проекцией без проверки доказательств.
Windows и macOS не наследуют статусы из Android, iOS или общего Flutter.

Каталог `product-map/features/` содержит сопоставления всех 23 текущих
parity-сценариев, функции регистрации и управления своими сеансами, а также
65 компонентов. Файлы используют JSON-совместимый
синтаксис YAML 1.2. Пути
компонентов разрешаются из авторитетного parity-реестра; каталог не хранит
вторую копию этих путей. Общий Web-компонент workspace указан один раз,
а Android- и iOS-адаптеры push отдельно. Охват функций за пределами parity,
серверные компоненты и остальные платформенные адаптеры ещё не полностью
инвентаризированы. Для серверных маршрутов и сервисов голосовых мелодий
добавлены проверяемые связи; сопоставление parity не подтверждает полноту карты.

Ещё не готовы: полноценный каталог и компонентный граф, ревизии поведения,
проверка поставок и откатов, полный интерактивный интерфейс, полный impact и контроль
изменений PR, а также приёмка AC-01…AC-18. Данные нельзя использовать для решения о
выпуске. Исходный parity-реестр остаётся авторитетным для своего покрытия.
