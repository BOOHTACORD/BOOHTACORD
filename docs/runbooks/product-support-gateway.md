# Публичная поддержка BOOHTACORD

Решение владельца и границы: [ADR-029](../adr/ADR-029-product-support-github-bridge.md), задача SP-002.
Обновлённая установка без явного локального назначения открывает по `?` обычный
парный DM с локальным служебным собеседником. Войти под ним нельзя, он скрыт
из каталогов людей. Администратор установки не может читать чужие обращения.

Перед первым сообщением пользователь видит предупреждение о публичности текста
и файлов в `Egkurilov/BOOHTACORD` и нажимает «Согласен на публикацию».
Согласие хранится отдельно для каждого пользователя и версии уведомления;
сервер отклоняет отправку без него, даже при обходе интерфейса. Обычные DM,
прежняя поддержка, cookies, telemetry payloads и локальные идентификаторы не
переносятся. GitHub получает только намеренно отправленный текст и файлы.

Старые клиенты не могут публиковать обращения, даже если тот же пользователь
уже дал согласие на другом устройстве. Для product DM сервер требует признак
поддержки публичного интерфейса `X-Boohtacord-Support-Publication: v1`;
без него возвращается `409 SUPPORT_CLIENT_UPDATE_REQUIRED`. Для обычных DM
и локального оператора обновление протокола отправки не требуется.

Первое сообщение создаёт один issue для диалога, следующие сообщения становятся
комментариями. Ответы с write/maintain/admin правами репозитория поступают в тот же
DM, с повторным использованием штатного ACL, unread и realtime. Комментарий
постороннего читателя не выдаётся за ответ оператора. Изменение/удаление сообщения
в локальном чате не удаляет уже опубликованную копию; интерфейс это объясняет.
Закрытие issue само по себе не является сообщением пользователю.

## Развёртывание шлюза

Шлюз обслуживает `https://metric.bootybay.ru/support/v1` в отдельном процессе;
это не OTLP и не разрешение отправлять DM в телеметрию. Исходящий доступ
установок работает за NAT. Подпись Ed25519 использует отдельный persisted seed,
проверяет метод, путь, digest тела, время и одноразовый nonce. Ключи GitHub
остаются у root-only брокера; клиентам и API-процессу шлюза они не передаются.

Код устанавливается root-owned в `/opt/boohtacord-support/<immutable-release>`.
До установки выполните Python 3.12+ tests:

```sh
python3 -m unittest discover -s tests/support_gateway -p 'test_*.py'
sudo python3 -m support_gateway.install --release /opt/boohtacord-support/RELEASE
```

Установка предназначена только для существующего ingress-хоста с авторизованным
`gh`, Python/OpenSSL Ed25519 и TLS `metric.bootybay.ru`. Скрипт проверяет
ожидаемую конфигурацию nginx и `nginx -t`, сохраняет OTLP authentication,
запускает `boohtacord-support-broker.service` и `boohtacord-support.service`.
Порт 9410 доступен только на loopback. SQLite/outbox/spool находятся в
`/var/lib/boohtacord-support`, mode 0700. Запросы и тексты не пишутся в access log.

API-процесс работает отдельным непривилегированным пользователем. Unix-брокер
принимает конечный набор операций только в фиксированном репозитории; shell,
другие URL/repositories и произвольные локальные файлы запрещены. Файлы читаются
через удерживаемый `O_NOFOLLOW` descriptor с проверкой размера и SHA-256.

Вложения публикуются в отдельном prerelease `boohtacord-support-attachments`,
с `make_latest=false`; это не выпуск приложения. Spool ограничен 512 MB,
опубликованные файлы удаляются из staging, остальные staging-файлы истекают
через сутки. Публичные копии в GitHub остаются. Лимиты: 200 публикаций шлюза
в сутки, 30 на ключ установки в час, nginx rate limit. Это публичная форма
обращения с криптографической изоляцией маршрутов, а не проверка личности человека.

## Эксплуатация и сбои

```sh
curl -fsS https://metric.bootybay.ru/support/v1/status
sudo systemctl is-active boohtacord-support-broker boohtacord-support
```

`ready=true` означает недавнюю успешную проверку GitHub. Не выводите routing DB,
GH config, seed, session tokens, тела сообщений или содержимое файлов в логи.
API установки использует только SQL outbox новых согласованных сообщений.
Сбой сети сохраняет очередь; подтверждённый POST идемпотентен. Если результат
публикации неизвестен, шлюз сверяет случайный public marker. Пока результат не
найден, слепой POST и последующие публикации того же диалога заблокированы.
Оператор разбирает такую неопределённость в защищённой среде, не очищая journal
и не меняя operation ID ради повторной отправки.

`PRODUCT_SUPPORT_ENDPOINT` позволяет задать иной доверенный HTTPS gateway;
без настройки используется адрес выше. Plain HTTP допустим только для loopback
в изолированных тестах. Browser cookies и GitHub credentials туда не копируются.
Явный локальный оператор/отключение сохраняются; команды описаны в
[локальном runbook](support-contact.md).

Смена репозитория public → private не удаляет прежние публичные копии. Обратная
смена повышает версию notice и требует нового согласия. Текущий этап принят
для публичного репозитория; приватные GitHub asset URLs требуют прав GitHub,
автоматического переноса файлов в новый private delivery backend здесь нет.

## Проверки

Повторяемые Web/Android/iOS сценарии проверяют явное согласие и постоянное
предупреждение на настоящем API, затем совместимость локального оператора.
Они не публикуют issue при каждом CI-прогоне. Контрольная публичная публикация
с синтетическим файлом и ответом оператора проверяется отдельно и фиксируется
в release evidence. Наличие unit tests или `ready=true` не заменяет этот прогон.
