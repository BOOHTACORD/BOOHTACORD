# ADR-029 — Общая поддержка продукта через GitHub

Статус: принято владельцем 2026-10-22 в текущей задаче; реализация и приёмка ещё не завершены.

## Решение владельца

Кнопка `?` всех установок по умолчанию открывает чат общей поддержки BOOHTACORD.
Первое сообщение нового обращения создаёт issue в `BOOHTACORD/BOOHTACORD`,
продолжение — комментарии. Ответы участников репозитория с write/admin-доступом
возвращаются в тот же локальный диалог. На первом этапе репозиторий публичный.
Публикация текста и файлов требует явного согласия пользователя; в чате всегда
показана публичность. История обычных DM и прежней локальной поддержки не экспортируется.

Это новое решение заменяет локальный-only сценарий SP-001/#516 только для
общей поддержки продукта. Глобальных пользовательских аккаунтов, discovery,
межсерверных обычных DM и пересылки media не добавляется. Локально явно
назначенная поддержка и явное отключение сохраняются.

## Границы

- В каждой установке — локальный служебный peer поддержки, не допускающий
  интерактивный вход или пользовательские sessions. Обычные pair-only ACL
  остаются, администратор не получает чтение чужих DM.
- Регистрация и запросы к шлюзу подписаны отдельным ключом установки,
  не session cookie и не opt-in телеметрией. Самостоятельно размещённому
  серверу не передаются GitHub credentials. Polling работает за NAT.
- Центральный шлюз хранит private routing/outbox, обеспечивает idempotency,
  ограниченные retries, проверку author permissions и защиту от echo loops.
  Credential broker допускает только фиксированные операции в одном репозитории.
- Файлы публикуются через штатные GitHub release assets отдельного prerelease,
  не latest app release. Нового публичного object store, backup или snapshot нет.
- В GitHub не добавляются installation/session/DM IDs, hostname,
  cookies, токены и существующая история. Public correlation markers — новые
  случайные идентификаторы операции шлюза, не полномочия доступа.
- Переход private → public требует нового согласия. Приватность GitHub
  наблюдается сервером; изменение видимости не объявляется удалением ранее
  опубликованных данных.
- Неопределённый результат GitHub POST сначала сверяется по public correlation
  marker; слепой повтор, создающий дубликаты, запрещён.

## Уточнение владельца от 2026-10-23 — автор и удалённые обращения

Новый issue получает заголовок `Обращение BOOHTACORD — user_id: <UUID автора>`.
Это явно разрешённое владельцем исключение для local account ID: Go worker
берёт UUID из `direct_message_messages.author_id`, а не из пользовательского
текста, client message ID или публичного API-параметра. Имя, email, установка,
DM и другие private identifiers не добавляются. UUID не предоставляет прав
доступа, pair-only ACL и согласие на публичное обращение сохраняются.

При подтверждённом удалении issue следующая неопубликованная реплика создаёт
новый issue; следующие сообщения и ответы используют новый маршрут. История
уже опубликованных сообщений не отправляется заново. Закрытие issue не равно
удалению. Только HTTP 404/410 при сохранённом доступе к репозиторию подтверждает
отсутствие issue; ошибки доступа, rate limit, 5xx и потеря ответа не разрешают
слепое создание дубликата. Неопределённый комментарий к подтверждённо удалённой
issue можно повторить в новом обращении: его прежняя публичная цель уже отсутствует.

Для постепенного обновления шлюз читает прежние payload без `user_id`. Повтор
той же operation может только дополнить отсутствующий UUID при неизменном
содержимом; заменить существующий UUID нельзя. Для старой очереди UUID может
быть взят из нового подписанного сообщения того же диалога той же установки.
Если UUID неизвестен, сохраняется прежний нейтральный заголовок без выдуманного
идентификатора. Сначала обновляется шлюз с брокером, затем Go API установок.

## Приёмка

Нужны focused tests до реализации, реальные PostgreSQL/Go/Web checks,
Android/iOS сценарии, публичный синтетический issue → ответ → тот же чат,
negative tests для чужой установки/пользователя, согласия, credentials,
повторов, сбоя после POST, files и отсутствия экспорта обычных DM.
До PASS фактических проверок новая интеграция не считается работающей.
