# ADR-032: Источники и доказательства карты продукта

- **Статус:** предложено в PR #699; реализация и приёмка #688 не завершены
- **Дата:** 2026-11-10
- **Область:** карта функций и архитектуры одного развёртывания BOOHTACORD

## Контекст

Команде нужна воспроизводимая карта функций, клиентских платформ и зависимостей.
Наличие общего Flutter-кода, зелёного unit-теста или Git-коммита не доказывает
публикацию отдельной сборки и работу на устройстве. Копирование существующих
реестров создало бы конфликтующие источники информации.

## Решение и источники

Карта — версионируемая проекция репозитория и проверяемых release/evidence
записей. Она не вводит новый backlog, сервер, базу данных или каталог обновлений.

| Данные | Владелец истины |
| --- | --- |
| Продуктовые требования | Утверждённый brief и `docs/specs/spec-voice-platform/SPEC.md`, CAP и REQ |
| Задачи и зависимости | `backlog/tasks.yaml` и GitHub Issues/PR |
| Существующие parity-сценарии, их тесты и пути | `tools/qa/local_features/features.json` и действующий parity validator |
| Формы API и событий | `contracts/` и связанные проверки контрактов |
| Новые имена функций, связи компонентов и ревизии поведения | Версионируемый `product-map/` |
| SHA, хеши и состав native-сборок | Действующий native asset contract и подписанный/проверенный manifest |
| Факт публикации и развёртывания | Проверенные release и deployment receipts соответствующего артефакта |
| Поведение в среде и на устройстве | Привязанное к SHA, платформе и среде evidence с фактическим результатом |

Генерируемые HTML и Markdown не редактируются вручную. Компонент с общим кодом
хранится один раз; связи с платформенными адаптерами и статус каждой ОС
раздельны. Сервер — зависимость клиента, а не шестая клиентская платформа.

## Идентичность и ревизии

Feature ID и component ID стабильны и различны. Существующие parity ID не
переименовываются; CAP/REQ, задачи T/SEC и номера GitHub не подменяют их.
Перенос файла не создаёт новую функцию. Исчезновение ID и переписывание старой
записи ревизии запрещены; вывод из эксплуатации требует сохраняемого tombstone
и проверяемого перехода. Alias не может совпадать с другим ID или alias.

Целочисленная feature revision описывает контракт поведения. Она не равна
номеру приложения, версии API или Git SHA. Новая семантика добавляет следующую
ревизию, не меняя прежние записи. Неизвестное значение остаётся неизвестным.
Для каждой клиентской платформы отдельно фиксируются применимость, состояние
и реализованная ревизия; исключения требуют объяснения и решения владельца.

## Независимые уровни подтверждения

1. **Source:** наличие и ревизия реализации согласно проверенному каталогу.
2. **Build:** snapshot на точном чистом SHA и проверенный manifest сборки.
3. **Release/deploy:** связь с опубликованными байтами и receipts; откат меняет
   текущую поставку, не переписывая состояние source или историю сборок.
4. **Runtime:** отдельное evidence конкретной платформы и среды; unit-тест или
   успешная сборка не превращаются в PASS физического устройства.

Без достаточной проверки результат — UNKNOWN, NOT_RUN, BLOCKED или FAIL, а не
выдуманный зелёный статус. Исторический релиз без snapshot остаётся UNKNOWN;
версия приложения не восстанавливает потерянную feature revision. Сравнение
source, поставки и runtime выполняется отдельно. Свежесть определяется по SHA
и происхождению записи, а не по дате последнего ручного редактирования.

## Управление изменениями и ограничения внедрения

Генерация должна быть детерминированной, проверки — работать на PR и merge
queue без write-токенов. Новые runtime-пути и изменения уже известных областей
должны иметь явную связь с функцией либо проверяемое решение об отсутствии
влияния. Существующие пропуски инвентаризации видны в baseline и не считаются
покрытыми. Удаление, перемещение и shared-контракты требуют impact-анализа.

На момент предложения покрыт только начальный каталог, а подтверждение полного
происхождения релизов, все платформенные адаптеры, blocking governance для
существующих путей и приёмка AC-01…AC-18 ещё не завершены. Это ADR не является
доказательством их выполнения и не разрешает production mutation ради проверки.

## Последствия

Команда поддерживает небольшой каталог недостающих связей и автоматическую
валидацию вместо второй копии parity, контрактов и release-каталога. Цена —
необходимость документировать осознанные ревизии и подтверждать каждую границу
доставки отдельно. При недостатке evidence карта остаётся неполной, а не
приписывает платформам одинаковую поддержку.
