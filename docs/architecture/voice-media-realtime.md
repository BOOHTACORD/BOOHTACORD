# Voice media and realtime

After a voice lease revocation commits, `voice.lease_revoked` addresses only the affected account with its own `{ "lease_id", "reason" }`. Reasons are `TRANSFER`, `KICK`, `CHANNEL_CLOSED`, `SESSION_REVOKED`, `BANNED`, `LOGOUT` or `VOLUNTARY_LEAVE`. A client stops only that lease's local lifecycle and must not infer that LiveKit has already removed a connected participant; the private SFU revocation outbox and signal guard remain authoritative. A retry may repeat a hint for the same lease, which is safe to deduplicate by lease ID and reason.

LiveKit credentials are minted through an authenticated API command only after the API creates or transfers a current voice lease. The reverse proxy exposes the client `/rtc` signaling path but not LiveKit's management API; it sends every signal connection through the private lease-admission guard. Browser clients pass the credential as the LiveKit `access_token` query parameter, while native desktop clients pass the same credential as `Authorization: Bearer`; admission accepts exactly one transport and validates identical lease-scoped claims. The proxy skips signaling URI logs, and admission never logs either credential transport. The API worker alone holds a private RoomService credential for participant removal; media tracks do not transit the Go API. A WebSocket interruption must not force a healthy WebRTC session to close, but the server can revoke admission on authoritative moderation events.

The screen-share panel displays the chosen target separately from browser capture settings and available LiveKit sender stats. Missing fields remain unavailable rather than being copied from the target profile; these local observations are never sent to API logs and are not POC or capacity evidence. A screen source reported as ended is stopped through the SDK before the UI offers a new explicit picker action.

The remote screen viewer reads only LiveKit `remoteParticipants` of the room joined by the current room-scoped credential. It joins with screen tracks unsubscribed, keeps unselected screen audio/video unsubscribed, and attaches only the explicitly selected stream to one local video/audio pair. Remote microphone publications are separately enabled and attached to owned local audio elements so ordinary room voice does not depend on a screen selection. Deafen mutes every such remote microphone element and the selected screen-audio element, disables the local published microphone, and restores only the microphone state that existed before deafen; it does not stop local screen publication. The credential retains its lease identity but carries signed `account:<UUID>` metadata, which the client validates before using it as a local volume-preference key. Participant microphone and selected-stream audio levels are separate `0…200%` Web Audio gains; if Web Audio cannot be created the UI keeps a truthful capped HTML-media fallback. Preferences are local to the deployment origin and authenticated browser account, survive a reload, and intentionally do not synchronize to another browser/device. Participant cards include every remote participant in the room, an observable `RemoteTrackPublication.isMuted` label and a persisted local volume even before that participant's audio track attaches. `ActiveSpeakersChanged` is intersected with the room's remote participants and rendered as text plus a visual dot; it neither inspects audio samples nor represents microphone permission, network quality, moderation state, a server-side metric or another user's deafen state. This client discipline does not prove SFU enforcement, metadata visibility, acoustic amplification quality, speaker-event behavior, remote mute propagation, prevent a malicious modified client, or satisfy the browser/Windows/macOS media POC.

The browser supplies a bounded LiveKit reconnect policy (six exponential attempts with jitter) and renders `RECONNECTING` separately from mute, listener mode and voluntary exit. It does not invent a post-disconnect rejoin after the SDK gives up: the current logical lease is released and a user must explicitly join again. This keeps a client reconnect loop from bypassing future kick, ban, logout, channel deletion or revocation enforcement; actual browser and SFU behaviour remain POC-03 evidence work.
