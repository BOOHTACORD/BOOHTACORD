# Issue 272: Flutter roster after prolonged outage

## Product behavior

On Android 15 emulator, using Flutter candidate source `e565420073483c7234202817eecf362cf754e844` from PR #693 with the unmodified master roster retry code, a synthetic Android listener and Chromium participant joined one owned channel. The isolated API and LiveKit were stopped together for 130 seconds and restarted. The Android voice session rejoined, and its authenticated API returned the nonempty roster with two participants. After a further 60 seconds the roster controller was still not fresh. Its UI offered manual retry; invoking that retry recovered a fresh roster. The acceptance test failed as intended (`QA272_AUTO_STUCK`, `QA272_MANUAL_FRESH`). The screenshot immediately after voice recovery showed `Состав недоступен`; original-resolution 1080 x 2400 image SHA-256 `5f27aff216d0d694b6d65c8f37dfbce8e4bbc5d72b686f65ca2e09d330d29c73`. The test's 60-second observation and manual control, not this immediate screenshot alone, establish the stuck state.

The Flutter retry loop stops after six transient failures. The change retains fast exponential retries, then continues one jittered retry every 24–30 seconds, bounded to one watcher and cancelled on stop/logout. 401 and 403 retain their existing terminal behavior; 404 and 410 now also stop automatic retries because the global roster endpoint is absent or gone. It does not alter server ACL, convert failures to empty lists, or claim a capacity SLO. This is an interim change to the currently shipped SSE client; the separate #689 migration has its own requirements.

## Fix verification

A focused test failed against the baseline before implementation; 25 roster controller/API/event tests passed after the change, including 24- and 30-second jitter bounds, a single slow timer, reset after fresh data, manual retry, 401, 403, 404, 410 and logout. Focused Dart analysis, base-relative client parity, and 18 LiveKit source-verification tests passed.

Two separate Android emulator real-stack repetitions used the same candidate #693 Flutter source plus this branch's sole production change `clients/flutter/lib/src/features/voice/roster_state/retry.dart` (working-file SHA-256 `ce5b895db5715f198a415de0f8483b18af57671172df2b539e888c6b63538982`). After a 130-second combined API/SFU outage, each run automatically returned a fresh authenticated roster with both synthetic participants within 60 seconds, without invoking manual retry; the browser and API control also passed. A screenshot after the second run was inspected at 1080 x 2400: the roster status read `Состав обновлён` and the channel showed both participants. SHA-256 `baf55ec4b1d832c32e7b24097087cfc6b97a6ca62ba76a4b41363fbbe55d68ae`. The same capture still showed separate chat/connection recovery UI; it is not proof of chat recovery. No physical audio, iOS/macOS, staging or production acceptance is claimed.

The executable fixture is built from the Windows combined-outage fixture documented in [the recovery record](https://github.com/BOOHTACORD/BOOHTACORD/blob/3b25fec76/evidence/qa/issue-648-android-sfu-only-2026-11-09.md) plus `roster-test.diff`; `web.cjs.txt` and `control.py.txt` are the synthetic peer and owner-guarded fault controller. This is combined-source evidence, not an exact-head build of this PR alone; the later 404/410 termination change was unit-tested and was not included in these emulator runs. Temporary ADB reverse mappings and owned containers were removed; the test package was absent afterwards. No real account, conversation, token or audio payload was recorded.

The local feature gate was attempted on Windows (`--feature auth --feature connection_status --feature screen --feature voice --platform android --native-device android:emulator-5556 --real-stack`). It returned FAIL: child `flutter` stages were BLOCKED and the native stage could not find a usable `python3` executable; there were no screenshots in that gate report. Separate emulator and unit results above do not convert that gate to PASS. Required broader #272 platform, load, ACL, production and rollback acceptance remains NOT_RUN, so the issue stays open.
