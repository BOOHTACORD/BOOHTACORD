# Issue 137: isolated NAT20 baseline

Observed 2026-11-07 UTC against backend source
`0332d2ed233e93533e799fffdc6d9c2fcbbb6764`. An owned loopback-only Docker
stack used the project's API image, PostgreSQL 17.6 and the normal default
login policies. All accounts and credentials belonged to this disposable
fixture. The 19 pre-seeded members received the disposable admin's valid
password hash in the isolated database; no production data was used.

| Scenario | Actual result | Status |
| --- | --- | --- |
| 20 distinct valid accounts, sequential login from one source | 10 HTTP 204 with cookies; 10 HTTP 429 without cookies, Retry-After 300 seconds | FAIL: NAT20 acceptance |
| Eight wrong passwords for one account | Eight HTTP 401 | PASS_SCOPED |
| Correct password immediately after the eight failures | HTTP 429, no cookie, Retry-After 30 seconds | PASS_SCOPED |
| Another valid account from that same source immediately afterward | HTTP 204 with cookie | PASS_SCOPED |
| `go test -count=1 ./internal/security/rate_limit ./internal/identity/admit_login ./internal/identity/login_user/api ./internal/config/runtime` | Four packages passed on Go 1.26.4 Windows/amd64 | PASS_SCOPED |

The API was restarted between the NAT20 cohort and the account-budget control
to reset in-memory counters. The test exercised actual HTTP, API, KDF and local
PostgreSQL; it did not independently verify issued session identities, test
multiple source IPs, simulate a physical NAT, or cover client UI and uploads.
Credentials, response cookies and user identifiers are not recorded here.

Current `docs/adr/ADR-003` explicitly specifies 10 login attempts per source in
five minutes. Merely raising that limit would change the accepted abuse-control
policy and would not establish an adequate replacement global work budget.
The defect remains open while the replacement policy, threat tradeoffs, ADR,
regression tests and real-stack acceptance are completed together.

The owned stack was stopped and its containers, private database and network
were removed by its normal cleanup routine. No production service was changed.

## Candidate `f919ae4b888fe1b07c0551f86d707008ce022c23`

A fresh owned stack built the candidate backend with its actual PostgreSQL and
loopback-only HTTP endpoint. Two logical source IPs were supplied through a
trusted private Docker proxy boundary, not a physical router NAT.

- Two cohorts of 20 distinct valid accounts: each 20 HTTP 204 and cookies.
  Twelve further logins from the first source were admitted; its 33rd received
  429 with Retry-After 300 and no cookie.
- Eight wrong passwords from eight logical sources returned 401; the next valid
  password for that account returned 429/30 without a cookie. A different
  account succeeded; after 32 seconds the first account succeeded again.
- A 220-request concurrent malformed-input burst from distinct logical sources
  returned exactly 200 HTTP 400 and 20 HTTP 429, all 20 with Retry-After and
  none with cookies. This checks global admission, not 220 KDF operations.
- At 150 seconds of a separate observation the global limit still returned 429
  with Retry-After 136; at 305 seconds a fresh request reached the handler and
  returned the expected malformed-input 400. The original window was not reset.
- A 64-way password burst across 20 known and 44 unknown fixture accounts
  returned 11 HTTP 204, 11 HTTP 401 and 42 HTTP 503 with Retry-After 1. No
  denied response had a cookie; a controlled valid retry after two seconds
  succeeded. This verifies bounded behavior, not a production capacity SLO.
- Ten malformed upload requests under one authenticated fixture account reached
  the handler (400); its eleventh received 429/300. A second account at the
  same logical source still reached the handler (400). This checks quota
  independence and not the transfer or ACL of an actual file.
- Nearest auth, password and limiter packages passed; auth-route, rate-limit,
  account-admission and password packages also passed `go test -race` on Linux.
  Web authentication-flow and retry tests passed (8 tests); Flutter's focused
  auth rate-limit tests passed (6 tests). Client tests use mocked transport.

Actual file transfer, end-to-end physical NAT, production capacity, and all
remaining original issue criteria are not implied by the results above. The
candidate adds a deployment-wide fixed window; a distributed actor can exhaust
that budget and deny legitimate logins until expiry, as discussed in ADR-003.
