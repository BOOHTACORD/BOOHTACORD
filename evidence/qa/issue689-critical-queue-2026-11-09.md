# Issue 689: critical revocation during queue overflow

- A focused test first failed after 65 ordinary targeted hints filled a 64-slot subscriber queue: a subsequent `voice.lease_revoked` disappeared during overflow acknowledgement. The hub now retains queued and subsequent revocations in a per-subscriber bounded reserve while ordinary overflow requests resynchronization. Acknowledgement returns those revocations to the socket queue before later ordinary events. If the reserve is full, durable targeted publication returns `ErrCriticalBackpressure`, so the voice outbox does not mark that notification emitted and can retry. Subscribers for other accounts do not receive the private event.
- PASS: five Linux `-race` repetitions of the complete `event_hub` and `connect_session` packages, including the 64/65 boundary, full critical-reserve retry, journal-failure preservation, 500 acknowledgement/publication races per repetition, and a real loopback WebSocket whose synthetic journal causes overflow during replay. Database-dependent tests are skipped in that no-DSN run; it is not a full release gate.
- PASS: a separate no-skip `notify_lease_revocation` package run against disposable PostgreSQL, plus vet/build. Its new integration test verified a saturated reserve left the real outbox row unmarked, and the notification was delivered after claim expiry and retry. Test events: `.out/checks/issue689-critical-backpressure-db-serial.jsonl`.
- Two broader three-package database runs failed after the disposable PostgreSQL stopped accepting connections: `.out/checks/issue689-critical-backpressure-db.jsonl` and `.out/checks/issue689-critical-backpressure-db-allserial.jsonl`. A third diagnostic attempt failed even at database preflight; the owned PostgreSQL reported `oom=false`, exit code 0 and a fast shutdown request before cleanup. The shutdown initiator is undetermined. The owned containers were removed. These failed runs are not counted as passing database integration.
- This protects the tested bounded queue/outbox paths. It does not establish delivery across a failed socket write, process crash, all client recovery races, real slow network, hardware/physical devices, or the full required load matrix. The implementation and tests remain on a dirty worktree, and complete WS-08 stays `NOT_RUN`.
