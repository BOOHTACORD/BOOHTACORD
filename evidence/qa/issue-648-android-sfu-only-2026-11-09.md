# Issue 648: isolated SFU-only recovery on Android emulator

Product source `8306413a84c224a712509d7a059916c95b00bd3c`; Android 15 Pixel emulator running a debug integration build. The real Go API, PostgreSQL and LiveKit were separate owned loopback containers; test-only harness ports were moved because another fixture occupied the defaults. A synthetic listener account joined a synthetic channel. No production service was modified.

LiveKit alone was stopped for approximately 88 seconds while the API remained running. The test observed reconnect/error/joining states and subsequently returned to listener mode in the original channel, approximately 19 seconds after LiveKit started. The test passed and its source-resolution 1080 x 2400 capture showed the channel and connected indicator; local screenshot SHA-256 `8199f0621c298dd5f26c3bc7e8b97c4cdb23b06a41f97965805e18d43b466ca9`. **Important timing correction:** reconnecting was observed approximately two seconds before Docker reported the stop as finished. The stop command had already been initiated, so this observation does not establish that reconnecting began before shutdown started; this run also does not establish a stable connected baseline immediately before the injected outage. There was no second participant or acoustic media verification.

A separate test stopped the same owned SFU immediately after the client reported readiness, waited for reconnecting, explicitly left the channel, and restarted SFU. The client remained out of the channel for 90 seconds and the test passed. The real test fixture used the original `issue648_manual_leave_test.dart` with only local QA port adaptation. The first recovery fixture additionally shortened its post-success hold from 90 to 15 seconds; state and channel assertions were unchanged.

Both tests used listener mode; production smoke, the combined fault matrix, measured credential renewal, handoff/ACL cases, physical devices and audio remain outside this result. The emulator test app and temporary reverse ports were absent after the run; the owned stack removed its containers. Issue #648 remains open.

The modified local fixture and controller are retained in `.out/qa648_api_test.dart` and `.out/qa648-api-control.py`. The emulator package and reverse mappings were absent afterwards, and the owned stack cleaned up. Other #648 acceptance requirements remain NOT_RUN.

## Windows real-stack recovery follow-up

Candidate Flutter source from PR #693 head `e565420073483c7234202817eecf362cf754e844` ran as a Windows debug integration application on the user's PC, using the retained `recovery.windows.dart.txt` test source in that PR and synthetic credentials. Preferences and secure storage were mocked in memory; the installed client's preferences file had the same SHA-256 before and after. The isolated Go API, PostgreSQL and LiveKit ran separately from production.

After two initial MediaConnectException failures using the fixture's default loopback ICE advertisement, the SFU was configured to advertise this PC's private interface. A temporary TCP forwarder accepted connections only from that same host and forwarded them to the loopback-bound owned SFU. This configuration admitted the listener, but the precise cause of the earlier failures remains unproven. The client remained in the original channel for a ten-second stable baseline, then the owned SFU was stopped for 45 seconds while the API remained up. After a failed retry, the test asserted `reconnecting`, the original channel ID and the visible recovery text. The SFU restarted, and the client returned to listener in the same channel; the full test finished PASS. It exercised Flutter Windows debug UI and real media signaling/transport, not the installed release binary, microphone/speaker audibility, or production. No Windows screenshot was collected or visually reviewed in this run.

The temporary forwarder and owned containers were stopped after the run. Windows manual-leave-during-outage, long multiple-minute outages, physical Android/iOS/macOS, final production verification, and the full issue matrix remain unverified. #648 remains open.

A second Windows run used the retained `issue-648-win-manual-leave-test.dart.txt` fixture, the same candidate source and isolated stack. After ten stable listener seconds, LiveKit was stopped. The test waited for an actual failed recovery admission, invoked the application's leave method and verified that recovery was cancelled and the channel cleared. LiveKit restarted, and the client remained out of the channel throughout 90 seconds of observation: PASS. This invokes the controller rather than physically clicking the leave button. The installed preferences hash was unchanged; owned services and the restricted forwarder stopped afterwards. It does not prove release-binary, acoustic or physical-device acceptance.

A third Windows debug run used the same local-only transport fixture and a 130-second SFU-only outage. The test source is the Windows recovery fixture in PR #693 plus `issue-648-win-long-lease.diff` in this branch; the controller held the SFU down for 130 seconds. After a ten-second stable baseline and failed recovery attempts, the client returned to listener in the original channel. The prior lease was non-null and the successful new lease was non-null and different: PASS. No lease IDs or tokens were logged. This establishes a new lease on a disruption longer than the configured one-minute token validity; it does not independently decode or verify the new JWT or test media audibility. The installed preferences hash was unchanged, and the forwarder and owned containers stopped.

A fourth Windows debug run repeated the same fixture and lease assertions with SFU stopped for 310 seconds. After restart the client returned to the same channel with a different non-null lease; the test completed PASS. API stayed running, the installed preferences hash was unchanged, and temporary services and the restricted forwarder were stopped. This establishes the five-minute SFU-only scenario, not fifteen minutes, combined API/SFU outage, installed-release or acoustic acceptance.

A fifth Windows debug run repeated the same fixture and lease assertions with the isolated SFU stopped for 910 seconds (15 minutes 10 seconds); API stayed running. The client remained in its recovery loop, then automatically returned to the original channel with a different non-null lease after SFU restart: PASS. The full test exited successfully after 16 minutes 25 seconds. It does not establish token contents, audio, release binary, combined API/SFU outage, production or other platform acceptance. Installed preferences were unchanged, and the temporary forwarder and owned containers stopped.
